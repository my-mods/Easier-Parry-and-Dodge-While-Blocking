# Native dodge guard recovery

The snapshots target Steam build 25129649 / CL-257186. Original assets and hashes are in `upstream/guard`.

Only `GA_Dodge` is shipped in the native container. It adds the existing `Player.Input.BlockTagAbilities` tag to `ActivationOwnedTags`. The engine owns this suppression for the dodge ability’s lifetime and removes it on end or cancellation. Forward dodge checks the native combat state after applying its effect. While the state is dodge (8), it starts the same native WaitDelay completion task used by side/back dodges, using Get Invincibility Time and the existing OnStateChanged listener. Either completion path releases suppression; a missing state-change event cannot leave forward suppression active indefinitely. A failed start ends immediately. Forward completion does not remove invincibility tags it never granted; cancellation unregisters the listener even when the invincibility flag is false. Stamina checks, animation selection, effect application and stock guard input handling are unchanged.

`GA_Input_CombatBlock.json` is an unmodified stock reference, excluded from the container. The game’s own guard ability listens for suppression-count changes: it lowers desired guard while the count is nonzero and restores it when the count reaches zero, provided the ability is still active.

Stock attacks retain both original paths: a successful combo handoff ends guard immediately; an attack release arms a listener that ends guard on the next attack press. The release listener fires immediately if attack is absent when guard starts, so guard-first input also arms cancellation for the first attack. If attack is already held when guard starts and its combo handoff fails, guard remains active until a subsequent release/press or another stock cancellation. Actual guard release and ability cancellation retain stock teardown. Once guard has ended, dodge completion cannot restart it without a fresh guard input.

Forward completion uses the native GetCurrentState getter and existing state-change and ability-end paths. It adds no guard bytecode, Lua hooks, polling or object searches. Forward dodge now also starts the existing native ability timer, using the game-configured duration rather than a fixed mod delay. It leaves stock guard listener lifetimes intact. It conflicts with other replacements of `GA_Dodge`; a separate mod replacing guard input can change its response to the suppression tag.

The Dodge while blocking setting selects the behavior of the current player's instanced dodge ability. Off removes only `Player.Input.BlockTagAbilities` from its `ActivationOwnedTags`; On includes it. `ActivationBlockedTags` is untouched, so Off retains the game's original activation checks. Four branch destinations in the cooked graph test that exact owned tag: without it they follow the original forward-completion, state-change, cancellation and timer paths; with it they follow the guard-recovery paths described above. All other executable exports remain stock. Shared class defaults and other actors' instances are unchanged by the settings worker.

The worker finds the instance through the player's owned ability specs. Before changing owned tags it checks the matching spec's reflected `ActiveCount` is zero, keeping tag ownership and the graph selection stable for an active dodge. Every read reacquires the borrowed spec and verifies the indexed instance. Session cleanup skips an active or replaced instance; the next session applies its desired setting through the same bounded worker. A persistently active or unavailable ability exhausts the 20-attempt readiness window without mutation and retries after a settings change or relevant lifecycle event. Existing unrelated tags are preserved. No activation-blocking tag is added.

Perfect dodge window reuses the same setup module and finite worker. It resolves the current local player's `PlayerCombatComponent`, calls native `GetConfig()`, and scales the config UObject's `PerfectDodgeWindow` float. The config can be a shared data asset: it is not cloned and must not be treated as player-owned memory. Only this scalar changes, and only when the selected percentage differs from 100. The native dodge graph reads it for perfect/ultra classification; direction, distance, invulnerability duration, cost and activation checks are unchanged. Repeated lifecycle events do not compound the value. Session cleanup restores a matching override and preserves values subsequently changed by another system. No borrowed struct or raw native address is retained for memory access.

Timing changes and ability discovery run in separate frames on the existing worker. Both On and Off check the owned dodge instance after save loading, allowing recovery of settings deferred by an active dodge in the previous session. The worker stops after success or 20 readiness attempts and can resume on player/map or relevant construction events. There is no recurring settings or input check and no Lua callback on each dodge.

The perfect-dodge route was checked against Steam build 25232147 / CL-258504: native `CombatComponentBase:GetConfig` returns a config UObject and the stock and packaged perfect-dodge graph exports match. These source and binary checks identify the route; they do not measure frame times or establish live gameplay behavior.

To reproduce the native payload, convert `src/guard/GA_Dodge.json` to a UE5.5 legacy asset using UAssetAPI-compatible JSON conversion, preserve its `/Game/_Dawnwalker/Combat/Abilities/Dodge/GA_Dodge` package path, and convert it to an UE5.5 IoStore container with retoc and the matching game script-object metadata. Do not include the stock guard reference in that container.
